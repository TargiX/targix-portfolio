## The pitch

Image generation tools are built around **one prompt at a time**. You type a sentence, wait for images, edit the sentence, and slowly lose track of what changed. That works for play. It falls apart when the prompt has structure: subject, setting, mood, references, model choice, variations, and a history you want to come back to.

Phosphene replaces the blank prompt box with a **visual workspace**. You compose prompt ingredients as zones and nodes, switch between feed, graph, flow, and template views, then let the app compile the structure into a generation request. The product is less "chat with a model" and more "keep the creative state legible while you iterate."

## What's in the box

- **Canvas modes**: a D3 graph for prompt exploration, a feed for generated images, a Vue Flow surface for chained modules, and template forms for guided workflows.
- **Prompt compiler**: shared services turn graph state, zones, template fields, references, and model settings into provider-ready prompts.
- **Generation layer**: Nuxt Nitro and tRPC routes fan out to Google/Gemini, fal.ai-hosted models, Alibaba/Qwen paths, and image-edit utilities.
- **Persistence**: Prisma and Postgres save users, dreams, generated images, graph state, model preferences, lineage, payments, and activity events.
- **Product plumbing**: Auth.js with Google and email/password, Paddle subscriptions/credits, Resend email, Turnstile, Redis-backed rate limits, Sentry, and PostHog.
- **Infra**: GitHub Actions builds the Nuxt bundle and deploys it to a self-managed Hetzner/PM2 setup with Hetzner S3-compatible object storage for generated image variants.

## Stack decisions worth defending

**Nuxt 4 over Next.** This is a heavy editor app, and Vue's reactivity model fits canvas state well: fewer footguns, less code. Server components were tempting, but the editor is fundamentally client-side anyway, so Nuxt's auto-imports and file-based server routes get out of the way.

**D3 plus Vue Flow as two separate surfaces.** The freeform prompt graph wants force layout, zones, positions, and weird interaction details. The flow surface wants modules, ports, and connections. Keeping those as different surfaces made the product easier to reason about.

**tRPC where the app is tightly coupled, Nitro endpoints where the boundary is external.** Internal dream/image/user flows get typed contracts. Webhooks, auth, storage, and provider calls stay as explicit server routes.

**Prisma + Postgres.** The state model goes well beyond users and images. It includes saved dreams, generated-image metadata, graph JSON, custom subjects, model preferences, branch/moment lineage, likes, payments, and rate-limit records. A boring relational core is the right kind of boring here.

**Provider adapters over running my own GPUs.** The catalogue changes quickly: Gemini/Nano Banana, Imagen, FLUX, Seedream, Qwen, GPT Image, utilities for upscale/inpaint/rotation. The app needs a stable product model while providers stay replaceable.

## What I am still tightening

- **One source of truth for editor state.** Feed, Graph, Flow, Templates, and Simple Create all want to look like separate products. They still need one canonical document underneath, or saved sessions and reloads get fragile.
- **Lineage without making the UI feel like Git.** Branches, moments, snapshots, image provenance, and "expand to graph" are powerful, but the interaction has to stay understandable to someone who only came to make an image.
- **Provider failure UX.** Image generation fails in provider-specific ways: rate limits, content filters, timeouts, bad reference images, model quirks. The product needs to explain those failures without dumping infrastructure into the user's face.
- **Self-managed ops discipline.** Running the app on my own Hetzner/PM2 setup is flexible, but it means deploy health, rollback paths, Sentry, PostHog, storage, and payment readiness all have to be treated as product work.

## The honest read

The hard part is not calling an image API. The hard part is making a creative system where the prompt structure, generated outputs, model choices, references, and history remain visible after the first exciting result. Phosphene is my attempt to turn that mess into an interface people can actually steer.
